# Agent workflow

Fission is a tool for the user's existing agent. It does not decide when an issue is solved. Keep all work in this repository; runtime state, wallet credentials and experiment records belong outside it.

Payments use MPP through Tempo CLI with charge intent, the exact USDC.e token and Tempo mainnet selected for both quotes and purchases. Changed payment terms fail closed. The VM backend is named `compute-mpp`; legacy provider records remain readable without resetting their payment history.

1. Run `fission capabilities` and `fission list --json`. Match the issue to an explicit profile and its hard requirements. Never silently substitute a runtime sandbox for a full VM, P2P, or a guaranteed-size build. `plan` returns `status: unavailable` and exit 2 before any quote/payment when requirements cannot be met.
2. Record the user's aggregate authorization with `budget --total-spend AMOUNT --approve`. This ledger applies across CLI invocations sharing `FISSION_HOME`. It cannot be reset or increased by repeating the command. Do not change state directories to evade an authorization. Amounts cover gateway charges; leave room in the user's overall budget for network fees.
3. Create `plan NAME --recipe RECIPE --duration DURATION --max-spend CREATION_CAP --total-spend TOTAL_CAP`. Optional `--profile`, `--cpu`, `--memory` (GiB), `--disk` (GiB), `--arch`, `--os`, and `--kind` express requirements. Resource floors are planning estimates, not measured workload performance guarantees. Runtime recipes explicitly have no reserved capacity. Leave enough total budget for commands, observations, artifact transfer, and shutdown.
4. For public source, pass `--repo https://github.com/OWNER/REPO --ref FULL_COMMIT`. Resolve the intended PR head to its 40-character SHA first. The remote checkout verifies HEAD and records submodule revisions. Private source is uploaded explicitly; never transfer GitHub or wallet credentials. Source checkout does not imply compiling the client.
5. Review the saved plan and call `open NAME --plan ID --approve` within the user's authorization. This purchases once and submits the `bootstrap` job. Observe with `job NAME bootstrap --refresh` or `wait NAME bootstrap --duration 5m --max-spend 0.01`. Provider running is not workload readiness. Wait exit 2 means its observation budget/time ended; the remote job may continue. Exit 1 means failure or an error. Inspect the returned phase.
6. Submit ordinary work with `run NAME JOB --duration DURATION -- COMMAND ARG...`. The guest supervisor bounds the foreground process group. Detached services started by a command can outlive that job and remain bounded by the workspace lease. Jobs run in `/workspace`; executables are at `/workspace/forge`, `/workspace/reth`, or `/workspace/tempo`. Use argv directly; use an explicit shell only when shell semantics are wanted. A job name is never reused, including after an ambiguous launch. `jobs NAME` lists saved job IDs locally. `job --refresh` observes its existing marker and never re-executes the command. Unknown is not failed and must not trigger a new equivalent job automatically.
7. Retrieve the job's returned `log` path and explicit outputs with `download NAME /remote/file NEW_LOCAL_FILE`. Individual modest files only. Stop writers before export; a changing file fails checksum validation. `close NAME --output NEW_DIR` exports the recipe's declared files plus bootstrap output, then terminates. It does not collect arbitrary job outputs. If no files are needed, use `--discard-output`. Close when the user considers the issue done, independently of PR state. A termination acknowledgement is followed by a status check; `termination_unknown` requires later observation before reporting cleanup complete.

## Recovery and limits

For the simplest VM flow, use `plan NAME --recipe foundry --cheapest --budget AMOUNT --region ams --duration 24h`. `--budget` replaces both spending caps; do not combine them. It is the requested whole-workspace gateway allocation, not aggregate authorization or a fees-inclusive wallet-spend guarantee. Planning preserves that allocation and caps creation at the actual final quote. At least 0.0003 remains as the existing lifecycle accounting floor; this does not estimate all future calls or exports. `--cheapest` requires this budget mode, an explicit 24-hour lease and region, and cannot be combined with a specific machine or an incompatible provider/kind. It selects the lowest successful quote in the capped shortlist, never a guaranteed global minimum. A changed quote fails; open never reselects. Plan JSON returns `paymentSubmitted: false` and executable `open` argv. Use those only within the user's existing authorization. The task itself is an explicit subsequent `run`; bootstrap success does not establish task completion.

The plan's `funding` object exposes validated Tempo chain/token identity, creation amount, allocation and remaining allocation. Network fees are excluded; wallet balance and funding shortfall are unknown. An agent can preview an existing authorized Glue Tempo-token refill policy using its returned argv (replace the policy placeholder). Match its `receiveToken` (`usdc.e`) and sender wallet to the payment; Glue's `token` is the swap input. Use Glue's payment-token mode for USDC.e. A new Glue target, swap input cap, cumulative swap budget, fee reserve or grant needs its own authorization; a VM quote supplies none of these. Fission neither runs Glue nor installs or changes its policies.

`foundry-source`, `reth-source` and `tempo-source` recipes select their matching source profile and require `--repo` plus an exact `--ref`. Use additional hardware flags to raise the floor. Bootstrap installs the checkout, native build dependencies and pinned Rust 1.95.0, then checks the compiler; it does not compile or start a node. Run `/workspace/build` in an ordinary bounded job to compile the selected release executables with `--locked`. A failed build leaves the ready workspace available for inspection and another explicitly named job. Successful binaries are copied to `/workspace`; `/workspace/build.json` records commit, local changes, toolchain, versions and hashes. Download that file and needed outputs explicitly. `close` exports `/workspace/source.json` and bootstrap output; source.json describes preparation, not a completed build. `/workspace/cargo`, `/workspace/rustc` and `/workspace/rustup` work without shell activation; pass `--manifest-path /workspace/source/Cargo.toml` to Cargo commands run outside the checkout. The fixed compiler may not support every historical/future revision; failure never triggers a silent toolchain change. Full-VM source compilation is not yet live-verified.

For VMs, configure `budget --vm-max-spend AMOUNT --approve` within the aggregate authorization. An optional `--profile PROFILE` ceiling and explicit discovery cap only narrow the global ceiling. Changing a ceiling requires user/operator authorization; an average is never permission to increase it. The ceiling bounds the entire workspace allocation, including creation and lifecycle headroom. It is rechecked on plan, open and payment reservation.

The aggregate ceiling may be lowered with `budget --total-spend AMOUNT --approve` when it still covers every retained allocation and configured VM ceiling. Requests and allocations remain unchanged. It can never be raised or reset by this command.

Run `machines --profile PROFILE --region ams --duration 24h` to dry-quote up to three cheapest compatible catalog plans under the ceiling. The mean, range and sample count describe that capped shortlist from one provider, not a market average. Empty results retain the hardware and spending requirements; never increase the cap or shrink the disk just to get an offer. CPU units are provider vCPUs; decimal disk GB are converted to GiB conservatively.

Select a returned machine with `plan NAME --provider compute-mpp --machine MACHINE --region REGION --duration 24h` plus the ordinary recipe/profile/budget flags. Explicit compute selection defaults to VM; an explicit incompatible kind is rejected. This backend uses Vultr Ubuntu 24.04 x64, a workspace-specific SSH key and a one-time management credential saved privately in the state directory. Never expose or commit these credentials. There is no automatic renewal or refund promise. Small-VM execution, detached jobs, deadline enforcement, file export and authenticated destruction have been observed; large disks and public P2P have not been exercised. Catalog matching is not a synced-node readiness claim.

If SSH provisioning ends before a bootstrap job is recorded, observe the same workspace and run `prepare NAME` explicitly to resume. Once bootstrap has been recorded, only observe it; never replay preparation or purchase. After a failed deletion acknowledgement, close makes one status observation; unresolved outcomes remain `termination_unknown`.

A VM ceiling, missing aggregate authorization or exhausted aggregate allocation rejected at the locked reservation boundary records `not_submitted`. No provider request escaped; a new plan within the existing authorization may reuse that name. This exception never applies to genuinely ambiguous paid requests.

`ui` opens the local terminal interface: arrows select, Enter shows details, Tab filters, and `s` sorts. Enter from a ready VM's detail opens SSH and returns to the interface on disconnect. `x` saves declared output and closes after a local confirmation; it does not save arbitrary job outputs. SSH credentials remain local, with agent forwarding disabled. `ssh NAME` provides the same interactive connection without the TUI. Agents should use the JSON commands rather than automate terminal keys.

`spending` reads saved transaction references and cached verified amounts. `spending --refresh` or `v` in the TUI makes free, read-only Tempo RPC queries. Amounts represent verified sender USDC.e outflow, including fees in that token; other assets and later refunds are excluded. Transactions are deduplicated globally. Missing or unreadable receipts remain unknown, and a shared transaction is not assigned in full to each workspace. These payment figures never replace the conservative authorization ledger. The TUI reloads local state only; `p` explicitly checks the selected provider using its existing request cap. Quitting does not terminate machines.

`list`, `status` and `watch` show cached observations. `status --refresh` checks the provider; `job --refresh` checks the workload. `watch --refresh --max-spend AMOUNT` polls within a separate foreground cap and the durable workspace allocation. Ctrl-C stops observing; provider expiry still applies. Remote job completion does not mean the machine is terminated.

Preserve unresolved records and call `reconcile NAME` to recover a saved creation response and observe the provider. It never repeats creation or bootstrap. A missing remote ID needs provider/payment investigation. A launch marker without a running/completed supervisor remains unknown. Check a stale operation lock's PID before removing only that lock after its process exits. Never discard receipts to retry payment.

Budget reservations retain the full request cap even when a call fails. They are conservative bounds, not a report of actual spend. Workspace allocations remain allocated after close. Two operation caps remain for termination/status; artifact retrieval needs additional room. A failed export does not stop provider expiry.

The `output.log` artifact basename is reserved for saved-plan bootstrap output. Custom JSON recipes contain `name`, optional `description`, `prepare` argv arrays, `artifacts` absolute remote file paths, optional `afterCheckout` argv arrays (requiring a source reference), and optional `readiness` argv arrays. Saved-plan bootstrap executes preparation, checkout and afterCheckout once in that order; readiness repeats every 15 seconds inside its deadline until every command exits zero. Keep probes read-only and bounded. Legacy `open --recipe` retains synchronous preparation and a creation-only cap and cannot use afterCheckout; use saved plans for the agent workflow.

`reth` is a private local development chain. The `reth-synced` recipe prepares pinned Reth 2.5.2, Lighthouse 8.2.2 and `/workspace/ethereum` on a full Linux x86 VM with systemd. It enforces the matching profile before quotes, retaining at least 32 GiB RAM and 2048 GiB disk. Bootstrap prepares tools; it does not import a snapshot or start nodes. No affordable synced deployment has been verified.

Before sizing Reth, select an exact manifest from [Reth snapshots](https://snapshots.reth.rs). Its headline sizes are compressed downloads. Reth 2.5.2 supports `reth download --chain mainnet --manifest-path FILE --full --print-plan-json --quiet`, which prints selected archives and `totalDownloadSize`/`totalOutputSize` bytes without downloading payloads. Use Reth's selection instead of reimplementing pruning or chunk arithmetic. Record the exact binary, manifest and invocation outside this repo; the JSON does not name the preset. For conservative sizing, add compressed and extracted totals plus an explicit allowance for consensus, growth, source/build files, OS/filesystem and extraction workspace, round upward to GiB, and pass `--disk GiB` to both `machines` and `plan`. That flag can only raise the profile floor. This coexistence envelope is not a measured peak; unresolved extra space means capacity remains unresolved. Archive requires more than the full-node floor. Minimal must be an explicit workload choice, never an automatic downgrade. Source preparation alone does not establish snapshot compatibility, retention settings or synced readiness.

For the full mainnet workflow, transfer that exact manifest and run `/workspace/ethereum download --manifest /workspace/manifest.json --sha256 DIGEST --extra-disk-gib ALLOWANCE` in a suitably bounded job. The guest re-runs the pinned planner and checks actual free space before downloading, then publishes `/workspace/ethereum-data/snapshot.json` only after successful import. This is a second gate, not a substitute for pre-quote sizing or an exclusive disk reservation against other jobs. Failed staging stays recorded and is never overwritten or automatically replayed; inspect it before any manual recovery.

Start with `/workspace/ethereum start --checkpoint-url TRUSTED_HTTPS_URL --checkpoint BLOCK_ROOT:EPOCH --max-head-age SECONDS` in a bounded job. Select and independently verify a recent mainnet checkpoint first. The controller records intent before starting its systemd units, binds RPC/Engine/consensus APIs to loopback, and waits for two ready observations with an advancing consensus execution payload. Both genesis identities, canonical execution payload, fresh head, connected peers and non-optimistic/online execution must match. Peer counts do not prove inbound reachability; head readiness does not imply historical consensus backfill. Public P2P needs execution TCP/UDP 30303 and consensus TCP/UDP 9000 plus UDP 9001. No validator keys or staking are involved.

`/workspace/ethereum status --max-head-age SECONDS` observes current units/readiness; `wait` with the same flag continues observing without starting anything. Startup success is a timestamped observation; a cached completed job is not a fresh health check. Startup/wait timeout ends the observer job while node services remain bounded by the VM lease. `stop` stops and verifies both recorded service cgroups. `restart` requires the same checkpoint/readiness flags and stops the prior pair before creating a new recorded invocation. An optional `--reth /workspace/CANDIDATE` copies that executable into a digest-addressed location; its database compatibility remains unverified. The pinned importer is never replaced, and there is no automatic rollback after a candidate may migrate data. Source recipes remain separate; budget build space and prepare a checkout explicitly or upload a built candidate.

This recipe's automatic exports contain only the static tool report and bootstrap output. Stop writers and explicitly download small snapshot/start reports or bounded journal excerpts before closing; do not export live growing logs or databases. Full snapshot import, public P2P and sustained synced operation still require live validation on adequate hardware.

Tempo's runtime recipe starts an isolated development chain at loopback port 8645. Its local block producer is not Tempo's production consensus network. Source profiles alone select hardware floors; use a source recipe to prepare the build environment, then an explicit compilation job. No automatic public-network transactions, validator enrollment, or vulnerability reproduction workflow is provided.
