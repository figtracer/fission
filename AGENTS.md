# Agent workflow

Loaner is a tool for the user's existing agent. It does not decide when an issue is solved. Keep all work in this repository; runtime state, wallet credentials and experiment records belong outside it.

1. Run `loaner capabilities` and `loaner list --json`. Match the issue to an explicit profile and its hard requirements. Never silently substitute a runtime sandbox for a full VM, Windows, P2P, or a guaranteed-size build. `plan` returns `status: unavailable` and exit 2 before any quote/payment when requirements cannot be met.
2. Record the user's aggregate authorization with `budget --total-spend AMOUNT --approve`. This ledger applies across CLI invocations sharing `LOANER_HOME`. It cannot be reset or increased by repeating the command. Do not change state directories to evade an authorization. Amounts cover gateway charges; leave room in the user's overall budget for network fees.
3. Create `plan NAME --recipe RECIPE --duration DURATION --max-spend CREATION_CAP --total-spend TOTAL_CAP`. Optional `--profile`, `--cpu`, `--memory` (GiB), `--disk` (GiB), `--arch`, `--os`, and `--kind` express requirements. Resource floors are planning estimates, not measured workload performance guarantees. Runtime recipes explicitly have no reserved capacity. Leave enough total budget for commands, observations, artifact transfer, and shutdown.
4. For public source, pass `--repo https://github.com/OWNER/REPO --ref FULL_COMMIT`. Resolve the intended PR head to its 40-character SHA first. The remote checkout verifies HEAD and records submodule revisions. Private source is uploaded explicitly; never transfer GitHub or wallet credentials. Source checkout does not imply compiling the client.
5. Review the saved plan and call `open NAME --plan ID --approve` within the user's authorization. This purchases once and submits the `bootstrap` job. Observe with `job NAME bootstrap --refresh` or `wait NAME bootstrap --duration 5m --max-spend 0.01`. Provider running is not workload readiness. Wait exit 2 means its observation budget/time ended; the remote job may continue. Exit 1 means failure or an error. Inspect the returned phase.
6. Submit ordinary work with `run NAME JOB --duration DURATION -- COMMAND ARG...`. The guest supervisor bounds the foreground process group. Detached services started by a command can outlive that job and remain bounded by the workspace lease. Jobs run in `/workspace`; executables are at `/workspace/forge`, `/workspace/reth`, or `/workspace/tempo`. Use argv directly; use an explicit shell only when shell semantics are wanted. A job name is never reused, including after an ambiguous launch. `jobs NAME` lists saved job IDs locally. `job --refresh` observes its existing marker and never re-executes the command. Unknown is not failed and must not trigger a new equivalent job automatically.
7. Retrieve the job's returned `log` path and explicit outputs with `download NAME /remote/file NEW_LOCAL_FILE`. Individual modest files only. Stop writers before export; a changing file fails checksum validation. `close NAME --output NEW_DIR` exports the recipe's declared files plus bootstrap output, then terminates. It does not collect arbitrary job outputs. If no files are needed, use `--discard-output`. Close when the user considers the issue done, independently of PR state. A termination acknowledgement is followed by a status check; `termination_unknown` requires later observation before reporting cleanup complete.

## Recovery and limits

`list`, `status` and `watch` show cached observations. `status --refresh` checks the provider; `job --refresh` checks the workload. `watch --refresh --max-spend AMOUNT` polls within a separate foreground cap and the durable workspace allocation. Ctrl-C stops observing; provider expiry still applies. Remote job completion does not mean the machine is terminated.

Preserve unresolved records and call `reconcile NAME` to recover a saved creation response and observe the provider. It never repeats creation or bootstrap. A missing remote ID needs provider/payment investigation. A launch marker without a running/completed supervisor remains unknown. Check a stale operation lock's PID before removing only that lock after its process exits. Never discard receipts to retry payment.

Budget reservations retain the full request cap even when a call fails. They are conservative bounds, not a report of actual spend. Workspace allocations remain allocated after close. Two operation caps remain for termination/status; artifact retrieval needs additional room. A failed export does not stop provider expiry.

The `output.log` artifact basename is reserved for saved-plan bootstrap output. Custom JSON recipes contain `name`, optional `description`, `prepare` argv arrays, `artifacts` absolute remote file paths, and optional `readiness` argv arrays. Saved-plan bootstrap executes preparation once; readiness repeats every 15 seconds inside its deadline until every command exits zero. Keep probes read-only and bounded. Legacy `open --recipe` retains synchronous preparation and a creation-only cap; use saved plans for the agent workflow.

`reth` is a private local development chain. A synced execution/consensus workload requires a compatible pinned snapshot, expansion and growth capacity, matching network/genesis, Engine API JWT, execution and consensus P2P, and readiness at a fresh head. `harness/ethereum-ready.py` is an observer for an already configured pair, not a deployment recipe. It accepts explicit chain ID and maximum head age and rejects optimistic/offline consensus. The unavailable `reth-synced` profile must not be reported as implemented.

Tempo's recipe starts an isolated development chain at loopback port 8645. Its local block producer is not Tempo's production consensus network. Heavy source profiles and Windows describe unmet requirements; do not claim those environments were provisioned. No automatic public-network transactions, validator enrollment, or vulnerability reproduction workflow is provided.
